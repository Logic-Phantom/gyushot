# 이미지 처리 파이프라인

모두 기기 안(브라우저 Canvas)에서 처리한다. 코드: `packages/image-core/src/browser/index.ts`.

1. **입력 검사** `decodeSource` — 20MB 초과 거부, 헤더 픽셀 수 4천만 초과 거부, 매직 바이트로 실제 형식 판별(확장자·MIME 선언을 믿지 않음).
2. **디코딩** `createImageBitmap(blob, { imageOrientation: 'from-image' | 'none' })` — EXIF 방향은 여기서 **한 번만** 반영. 이후 회전(90° 단위)은 사용자 회전만 더한다(중복 회전 방지). HEIC는 디코딩되면 처리, 실패하면 "현재 HEIC는 지원하지 않아요".
3. **크롭 계획** `planCrop` — cover: 목표 비율 최대 영역 ÷ 확대 배율, 중심은 이미지 안으로 보정. contain: 전체를 넣고 여백.
4. **렌더** `renderToCanvas` — 출력 픽셀 캔버스에 아핀 행렬로 그림. 축소 배율 < 0.5면 절반씩 미리 줄임. JPEG이거나 contain이면 배경색을 먼저 칠함(투명 PNG→JPEG 자동 흰색 합성 대신 배경색 선택 제공).
5. **인코딩** `encodeCanvas` — `canvas.toBlob(mime, quality)` 결과의 매직 바이트가 요청 형식이 아니면 실패(위장 금지). DPI 기록 요청 시 JFIF density / pHYs를 직접 패치.
6. **용량 탐색** `searchQuality` — 사용자 품질(기본 80%)로 먼저 인코딩 → 상한 이하면 그대로. 넘으면 하한 40%를 시도해 불가능 여부를 바로 판단, 가능하면 이분 탐색(최대 8회, 8초). 각 시도는 DPI 패치까지 끝난 **최종 바이트**로 비교. PNG는 품질이 없어 한 번 인코딩 후 상한 비교.
7. **재검사** `inspectBlob` — 결과 Blob을 다시 디코딩해 픽셀, 바이트, 매직 바이트 형식, DPI, Exif APP1 유무를 읽음.
8. **판정** `validateOutput` — 가로·세로(허용 범위), 형식, 용량(상한 이하), DPI(기록 요청 시, 실패는 경고), EXIF 제거, 사진 내용(공식 인물 규격은 항상 `확인 필요`).

## 실측(브라우저, 2026-11-14, 데스크톱 Chromium 내장 브라우저 — 실기기 아님)

| 입력 | 설정 | 결과 |
|---|---|---|
| 예시 사진 271×350 JPG | 여권 온라인, JPG 80%, ≤500KB, 300dpi | 413×531 · 20KB · JPG · 300dpi 재확인 · EXIF 없음 |
| 예시 사진 277×350 + 90° 회전 | 반명함 300dpi | 354×472 · 14KB · 300dpi |
| 노이즈 3000×4000 JPG(9.9MB) | JPG 시작 품질 100%, ≤150KB | 7회 탐색, 품질 96.3%, 118KB, 235ms |
| 같은 입력 | PNG 무손실, 300dpi | 570KB, pHYs 300dpi 재확인 |
| 같은 입력 | WebP, ≤200KB | 126KB, WebP 확인 |

## 알려진 한계

- 토스 앨범 API는 `maxWidth`로 줄인(재인코딩된) 이미지를 준다 → 원본 EXIF·원본 해상도가 아닐 수 있음(D-011, 실기기 확인 필요).
- WebP DPI는 기록하지 않음(D-008).
- 미리보기와 결과는 같은 행렬을 쓰지만, 미리보기는 줄인 사본이라 아주 미세한 차이가 있을 수 있음.
- 메모리 부족 시 브라우저가 캔버스 생성을 실패시키면 `render-failed`로 안내하고 원본·편집 상태는 유지.
